# ЗАДАЧА

Создай с нуля production-ready интерактивный промо-сайт для музыкального объединения **«Южный соус»** и будущего микстейпа **«Южный соус: Эмо коммьюнити»**.

Это НЕ обычный лендинг.

Сайт должен ощущаться как странный, немного сюрреалистичный интерактивный интернет-объект, который пользователь сначала воспринимает как непонятную игру/эксперимент, а только в самом конце понимает, что всё это было промо музыкального релиза.

Главный принцип:

> **сначала любопытство → затем взаимодействие → затем зависимость от механики → затем раскрытие → пресейв**

Не раскрывай музыкальную составляющую до финальной сцены.

---

# 1. ТЕХНОЛОГИИ

Используй:

* Vite
* React
* TypeScript
* Framer Motion
* CSS / CSS Modules
* Howler.js или Web Audio API для звуков

Не используй Next.js без реальной необходимости.

Не используй Three.js/WebGL, если визуальный эффект можно сделать обычным DOM/CSS/Canvas.

Цель — максимально быстрая загрузка и плавная работа на мобильных устройствах.

Архитектура должна быть компонентной.

Предполагаемая структура:

Визуальный референс по духу:

* weird web
* старый интернет
* интерактивный арт-сайт

Он должен выглядеть немного **неправильно**.

---

# 3. ПЕРВЫЙ ЭКРАН

При первом посещении пользователь видит абсолютно чёрный экран.

В центре:

```text
СОУС
```

Под ним:

```text
[ ВОЙТИ ]
```

Минималистичная типографика.

Никакого логотипа.

Никакого названия «Южный соус».

Никакого упоминания музыки.

Никаких объяснений.

Кнопка должна ощущаться немного странной.

При наведении:

* лёгкий pixel distortion;
* небольшое смещение;
* едва заметное изменение tracking;
* возможно короткий digital click.

На мобильном hover-эффект заменить на touch interaction.

---

# 4. НАЖАТИЕ «ВОЙТИ»

После нажатия:

1. кнопка исчезает;
2. текст «СОУС» исчезает;
3. экран остаётся чёрным;
4. возникает короткая задержка примерно 500–1000 ms;
5. начинается открытие «глаза».

Не делай обычный fade.

Чёрный экран должен физически раскрываться по центру, будто это веки.

Используй CSS clip-path / mask / SVG mask или другой лёгкий способ.

---

# 5. ГЛАЗ

После открытия появляется сцена, снятая сверху.

Пользователь как будто смотрит **своими глазами на стол**.

Сцена:

* стол;
* картошка фри;
* ёмкость с соусом;
* возможно салфетка;
* возможно небольшие случайные детали.

Всё это 2D.

Никакого 3D.

Изображение должно иметь ощущение реальной фотографии, но обработанной под стилистику сайта.

---

# 6. МОРГАНИЕ

Очень важная деталь.

Глаз не должен быть просто маской, которая один раз открылась.

После открытия он должен периодически слегка «моргать».

Не делать полноценное закрытие каждые 2 секунды.

Нужно ощущение живого глаза:

* небольшое затемнение сверху/снизу;
* медленное сужение;
* лёгкий blur;
* кратковременное закрытие;
* снова открытие.

Интервалы должны быть немного непредсказуемыми.

Например:

```text
4.2 sec
7.8 sec
5.1 sec
9.3 sec
```

Используй randomised timing.

Во время взаимодействия моргание можно временно отключать, чтобы оно не мешало пользователю.

---

# 7. КУРСОР / РУКА

Это ключевой элемент сайта.

Пользователь не должен просто нажимать кнопки.

Вместо стандартного курсора используется **пиксельная рука**.

Но рука НЕ нарисованная.

Используются реальные фотографии руки пользователя/модели, обработанные в pixel-art / low-resolution стиле.

То есть:

> реальная рука → фотография → pixelated обработка → покадровая анимация

На desktop:

* стандартный cursor скрыт;
* рука следует за pointer;
* положение руки зависит от координат курсора;
* рука слегка запаздывает за курсором;
* движение имеет небольшую инерцию;
* при приближении к картошке/соусу рука меняет состояние.

На mobile:

* никакого постоянного отображения руки под пальцем;
* рука должна появляться в зоне touch interaction;
* движение должно ощущаться естественно;
* использовать Pointer Events, а не отдельно mouse/touch logic.

Используй:

```text
pointerdown
pointermove
pointerup
```

а не только:

```text
mousedown
mousemove
touchstart
```

Это позволит использовать одну систему для desktop и mobile.

---

# 8. СОСТОЯНИЯ РУКИ

Предусмотреть несколько состояний:

```text
idle
approaching
grabbing
holding
dipping
eating
waiting
```

Каждое состояние может иметь собственный sprite/frame sequence.

Например:

```text
hand_idle.webp
hand_move.webp
hand_grab.webp
hand_hold.webp
hand_dip.webp
hand_eat.webp
```

Если исходники предоставлены в виде отдельных фотографий:

* автоматически организовать их как frame sequence;
* не пытаться заменить покадровую анимацию одной CSS-анимацией;
* сохранить ощущение физической фотографии.

---

# 9. ПЕРВАЯ КАРТОШКА

После появления сцены пользователь должен интуитивно понять, что можно взять картошку.

Можно использовать очень маленькую подсказку:

```text
возьми
```

Но она должна быть почти незаметной.

Не делать большой UI.

Пользователь подводит руку к картошке.

При попадании в интерактивную область:

* рука немного меняется;
* картошка слегка двигается;
* появляется небольшой звук;
* курсор/рука получает feedback.

При нажатии:

```text
grab
```

Рука берёт картошку.

Картошка становится привязанной к руке.

---

# 10. СОУС

После того как картошка взята:

пользователь должен переместить её к соусу.

При приближении к зоне соуса:

```text
макни
```

может появиться маленькая подсказка.

При попадании в sauce zone:

* картошка погружается в соус;
* появляется небольшая физическая/маслянистая анимация;
* можно добавить звук;
* на картошке визуально появляется соус.

Не использовать тяжёлую физику.

Достаточно transform + небольшого rotation + scale.

---

# 11. ЕДА

После того как картошка обмакнута:

пользователь должен переместить её вверх, за пределы сцены / к условному месту рта.

При достижении зоны:

```text
eat
```

Картошка исчезает.

Можно сделать короткий звук.

После этого:

* рука исчезает;
* короткая пауза;
* возвращается новая картошка.

---

Пример:

```text
макни

```

Создай примерно 5–7 циклов.

Каждый следующий цикл немного отличается.

Например:

### Cycle 1

Спокойный.

```text
возьми
```

### Cycle 2

```text
ещё
```

### Cycle 3

```text
ещё?
```

### Cycle 4

```text
ЕЩЁ
```

### Cycle 5

```text
ЕЩЁЁ
```

### Cycle 6

```text
ЕЩЁ ЕЩЁ ЕЩЁ
```

### Cycle 7

Картошки больше нет.

---

# 14. КАРТОШКА ЗАКАНЧИВАЕТСЯ

После нескольких циклов пользователь пытается взять картошку.

Но её нет.

Рука начинает искать.

Она:

* двигается по столу;
* заглядывает рядом;
* проверяет упаковку;
* возвращается.

Появляется текст:

```text
ещё?
```

Потом:

```text
ЕЩЁ?
```

Пауза.

Рука продолжает искать.

---

# 15. СТРАННЫЙ МОМЕНТ

После нескольких секунд рука останавливается.

Она поворачивается в сторону камеры.

Будто смотрит на пользователя.

На экране:

```text
картошка кончилась.
```

Пауза.

Потом:

```text
а соус остался.
```

Очень короткая пауза.

После этого глаз начинает снова закрываться.

---

На чёрном фоне появляется:

```text
ты тоже не смог остановиться
```

Пауза.

```text
ещё.
```

Пауза.

```text
ещё.
```

Пауза.

```text
ещё.
```

Экран полностью становится чёрным.

# 17. РАСКРЫТИЕ

После короткой тишины появляется:

```text
ЮЖНЫЙ СОУС
```

Затем:

```text
ЭМО КОММЬЮНИТИ
```

Затем:

```text
МИКСТЕЙП
```

Можно сделать появление не обычным fade-in, а через:

* pixel reveal;
* короткий glitch;
* character-by-character reveal;
* distortion.

После этого начинается музыкальный фрагмент.

---

# 18. ФИНАЛЬНЫЙ ЭКРАН

Финальный экран должен быть очень простым.

Например:

```text
ЮЖНЫЙ СОУС

ЭМО КОММЬЮНИТИ

МИКСТЕЙП

[ ПРЕСЕЙВ ]
```

Также:

```text
релиз: [DATE]
```

Если есть обложка микстейпа — показать её.

Кнопка пресейва должна быть единственным очевидным CTA.

Не перегружать финальный экран.

---

# 19. ПРЕСЕЙВ

URL пресейва вынести в отдельную конфигурацию:

```ts
export const RELEASE_URL = "...";
```

Не хардкодить URL внутри компонентов.

Клик по CTA должен открывать реальный пресейв.

Предусмотреть возможность легко заменить:

* URL;
* название релиза;
* дату;
* аудио preview;
* обложку.

---

# 20. ЗВУК

Звук должен быть частью атмосферы.

Не включать музыку автоматически сразу после входа.

На первом этапе использовать только микрозвуки:

* click;
* grab;
* dip;
* sauce;
* eating;
* subtle room noise;
* digital noise;
* glitch.

Звук должен быть тихим и немного странным.

После финального reveal можно включить музыкальный preview.

Если браузер запрещает autoplay:

* корректно запускать аудио после первого пользовательского interaction.

Добавить mute/unmute.

Кнопка mute должна быть максимально незаметной.

---

# 21. АНИМАЦИЯ

Избегать ощущения «идеального motion design».

Анимации должны быть:

* немного медленными;
* физическими;
* местами дёргаными;
* с небольшой задержкой;
* иногда чуть непредсказуемыми.

Особенно рука.

Она не должна двигаться как игровой UI cursor.

Она должна выглядеть как **настоящая рука, которая пытается что-то взять**.

---

# 22. РАБОТА С POINTER

Создай единый abstraction:

```ts
usePointer()
```

Он должен возвращать:

```ts
x
y
isPressed
velocity
```

Использовать его для:

* руки;
* интерактивных зон;
* hover states;
* mobile touch;
* drag interaction.

Не привязывай интерактивность к абсолютным пиксельным координатам.

Используй нормализованные координаты:

```ts
x: 0..1
y: 0..1
```

Так сцена будет адаптироваться к разным экранам.

---

# 23. АДАПТАЦИЯ MOBILE

Это обязательное требование.

Сайт должен одинаково хорошо работать на:

* iPhone;
* Android;
* desktop;
* laptop;
* планшете.

На mobile:

* учитывать safe-area;
* использовать `100dvh`, а не только `100vh`;
* отключить browser overscroll;
* отключить случайный text selection;
* отключить image dragging;
* использовать `touch-action`;
* все интерактивные области сделать достаточно большими;
* не заставлять пользователя попадать пальцем в маленький пиксель.

Не делать отдельную мобильную версию сайта.

Одна сцена должна адаптироваться responsive-логикой.

---

# 24. PERFORMANCE

Это критично.

Сайт должен загружаться быстро даже на мобильном интернете.

Требования:

* WebP/AVIF;
* lazy loading там, где возможно;
* preload только критических assets;
* sprite sheets вместо сотен отдельных DOM images;
* не держать огромные оригинальные фотографии в браузере;
* оптимизировать фотографии руки;
* не использовать тяжёлые библиотеки без необходимости;
* не создавать тысячи React re-renders при движении pointer.

Pointer movement должен обновлять визуальное положение через:

* Motion values;
* requestAnimationFrame;
* CSS transform;

а не через постоянный React state update.

---

# 25. ASSETS

Я положу исходники в директорию проекта.

Не предполагай заранее названия файлов.

Сначала проанализируй содержимое `assets/`.

Определи:

* фотографии руки;
* фотографии картошки;
* фотографии соуса;
* фон/стол;
* возможные дополнительные элементы;
* звуки;
* музыку;
* обложку.

Если ассеты имеют последовательность кадров — используй их как animation sequence.

Если каких-то ассетов не хватает:

создай временные placeholder assets и пометь их TODO.

Не заменяй мои реальные исходники своими случайными SVG/emoji.

---

# 26. ОБРАБОТКА ФОТОГРАФИЙ

Если исходные фотографии руки выглядят слишком реалистично:

обработай их в CSS/Canvas или подготовь pipeline, чтобы получить:

* уменьшенное разрешение;
* pixelated edges;
* limited color palette;
* лёгкий noise;
* контраст;
* прозрачный фон, если необходимо.

Но сохрани узнаваемость реальной фотографии.

Цель:

> **фотография человека, которая выглядит как покадровая пиксельная анимация**

а не:

> нарисованная пиксельная рука.

---

# 27. КУРСОР

На desktop стандартный cursor должен исчезать только внутри основной интерактивной области.

Использовать кастомную руку.

При взаимодействии:

```text
idle → move → grab → dip → eat
```

Рука должна иметь небольшой trailing effect.

Например:

```text
pointer
   ↓
hand position
   ↓
slight lag
```

Но не переборщить.

---

# 28. СОСТОЯНИЕ ПРИ ЗАГРУЗКЕ

Добавить preload screen, но НЕ делать стандартный:

```text
Loading 73%
```

Лучше:

```text
...
```

или вообще чёрный экран.

Пока критические assets загружаются, показывать минимальный индикатор.

Главное — чтобы пользователь не увидел сломанную руку/пустой фон.

---

# 29. ACCESSIBILITY

Несмотря на экспериментальный характер:

* кнопка «ВОЙТИ» должна быть keyboard accessible;
* кнопка пресейва должна иметь нормальный focus;
* добавить reduced-motion режим;
* не делать сайт полностью зависимым от hover;
* для `prefers-reduced-motion` сократить сложные эффекты.

---

# 30. НЕЛЬЗЯ

Не делать:

* стандартный navbar;
* footer;
* «О нас»;
* соцсети на первом экране;
* описание группы;
* музыкальный плеер сразу;
* стандартные CTA;
* длинные тексты;
* cookie-попап;
* стандартный loading spinner;
* 3D;
* WebGL без необходимости;
* React-компоненты ради компонентов;
* чрезмерный glitch;
* чрезмерную анимацию;
* визуальный шум, который мешает взаимодействию.

---

# 31. АРХИТЕКТУРА СОСТОЯНИЙ

Сделай конечный state machine:

```text
INTRO
↓
EYE_OPENING
↓
TABLE_REVEAL
↓
INTERACTION_1
↓
INTERACTION_2
↓
INTERACTION_3
↓
INTERACTION_4
↓
INTERACTION_5
↓
INTERACTION_6
↓
NO_FRIES
↓
REALIZATION
↓
EYE_CLOSING
↓
REVEAL
↓
RELEASE
```

Не определяй всю логику через десятки независимых boolean:

# 32. ВАЖНАЯ ЛОГИКА

Пользователь не должен иметь возможность сломать последовательность.

Например:

* нельзя взять вторую картошку во время eating;
* нельзя макать картошку дважды, если состояние уже другое;
* нельзя вызвать reveal повторно;
* нельзя случайно нажать куда-то и перескочить сцену.

Но при этом взаимодействие не должно ощущаться как строгая игра.

Пользователь должен чувствовать свободу.

Сайт должен быть странным, смешным и запоминающимся, но при этом технически аккуратным.
